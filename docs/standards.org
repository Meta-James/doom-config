#+TITLE: Standards — Rules That Apply Across All Phases
#+AUTHOR: James Cook
#+STARTUP: overview
:PROPERTIES:
:ID:       docs-standards
:END:

Durable rules for this configuration, independent of which phase or subsystem is
being worked on. Phase-specific detail belongs in [[id:ai-architecture][docs/ai/]] or later
phase directories, not here.

* Doom-first
:PROPERTIES:
:ID:       std-doom-first
:END:

- Prefer Doom modules and abstractions (=package!=, module flags, =use-package!=,
  =after!=, =map!=, =set-popup-rule!=, =load!=, =add-hook!=, =setq-hook!=) over
  generic vanilla Emacs configuration.
- Never use =package-install=, =package-selected-packages=, or a second package
  manager alongside straight.
- Vanilla Emacs code is acceptable when it's genuinely the correct tool — say so
  explicitly when it is, don't default to it out of habit.

* Evil-first
:PROPERTIES:
:ID:       std-evil-first
:END:

Don't design workflows that fight Evil states or Doom's modal conventions. Account
for normal, insert, visual, motion, operator, and Emacs states where relevant.

* Org-first documentation
:PROPERTIES:
:ID:       std-org-first
:END:

Canonical architecture, inventory, decisions, workflow, and roadmap documentation
is Org, using Org's real capabilities (property drawers, IDs, TODO states, tags,
tables, LOGBOOK, source blocks) — not just files with an =.org= extension.
Markdown is fine for files an external tool conventionally requires: =CLAUDE.md=,
=AGENTS.md=, =.claude/rules/*.md=, executable prompt assets under =prompts/=.

* Cloud-first
:PROPERTIES:
:ID:       std-cloud-first
:END:

Use frontier hosted models for primary workflows. Local models only for a concrete,
named benefit (privacy, offline operation, low-cost bulk work, fallback) — never
build local-model infrastructure merely because it's possible.

* External binaries allowed, but documented
:PROPERTIES:
:ID:       std-binaries
:END:

Every external binary this config relies on needs, somewhere in
[[id:docs-inventory][inventory.org]]: a documented role, install method, version check, upgrade
method, and rollback/removal method.

* Commit, push, and history-rewrite authority
:PROPERTIES:
:ID:       std-no-commit
:END:

- The agent may commit, push, amend, rebase, reset, clean, or otherwise
  rewrite Git history — but only after proposing the specific command (and,
  for commit, the message; for push, the target) in conversation and
  receiving explicit, in-the-moment permission. A past approval doesn't carry
  forward to the next commit/push/rewrite.
- Read-only Git commands and diffs are always fine, no permission needed.
- Backed technically, not just instructionally: a committed
  =.claude/settings.json= =permissions.ask= list forces a Claude Code
  confirmation prompt on =git commit=/=push=/=rebase=/=reset=/=clean= for any
  session in this repo — it can no longer run unattended. See
  [[id:adr-agent-git-authority][ADR-015]] (supersedes [[id:adr-permission-enforcement][ADR-009]], which blocked these outright).

* Credentials
:PROPERTIES:
:ID:       std-credentials
:END:

- Never hardcode, print, log, echo, or commit secret values.
- Prefer Doom's =:tools pass= module, Emacs =auth-source=, or a provider's own
  official login flow over hand-rolled shell wrappers.
- Redact tokens from all documentation and command output — entry *names* are fine
  to record, values never are.
- See [[id:ai-providers][docs/ai/providers.org]] for the concrete credential map.

* No redundant tool duplication
:PROPERTIES:
:ID:       std-no-duplication
:END:

- One chat client, one inline-completion engine, one primary agentic-coding
  frontend at a time.
- A secondary tool needs a clearly distinct, frequently-useful responsibility the
  primary tool can't cover well — "it's popular" or "it supports another model" is
  not sufficient justification on its own.
- "Responsibility" is scoped per *axis*, not per broad category. Corfu and
  Vertico coexist because in-buffer and minibuffer completion are different axes
  ([[id:adr-corfu-migration][ADR-021]]); ponytail, caveman, and rtk coexist
  because code volume, prose register, and tool-output volume are different axes
  ([[id:adr-token-reduction-stack][ADR-023]]). Two tools on the *same* axis is
  the violation.
- A tool whose always-on token cost is paid every session must have that cost
  recorded when it's adopted — see the table in
  [[id:adr-token-reduction-stack][ADR-023]].

* No premature scope expansion
:PROPERTIES:
:ID:       std-no-scope-creep
:END:

- Don't activate or redesign EXWM until its own phase.
- Don't build the full Org Agenda system until its own phase.
- ~~Don't migrate this entire configuration to literate programming.~~
  *Superseded 2026-08-29 by [[id:adr-literate-config][ADR-035]]*, which did
  exactly that: =config.org= is now the single source of truth and tangles
  =init.el=, =packages.el=, =config.el=, =~/.bashrc=, =~/.inputrc= and
  =~/.gitconfig=. The rule stood while the config was three hand-edited files
  and the shell layer kept silently reverting; the ADR resolved both.
- Don't create a private Doom module (=config/development.el= etc.) until a
  subsystem is stable enough to justify the split.

* Human authority
:PROPERTIES:
:ID:       std-human-authority
:END:

- Ask for approval at architectural and destructive boundaries.
- Tests and formatters may run automatically once a stage is approved.
- Package installs, system upgrades, broad rewrites, deletions, and permission
  changes require explicit, current-turn approval — a prior approval doesn't
  carry forward to a new category of action.
- The agent may commit, push, and rewrite Git history, but only with
  explicit, current-turn approval for each one — see [[id:std-no-commit][std-no-commit]] and
  [[id:adr-agent-git-authority][ADR-015]].

* Host scope
:PROPERTIES:
:ID:       std-host-scope
:END:

There is more than one machine — the desktop =PsychedPC= and James's laptop —
and one repository shared between them. See
[[id:adr-multi-host-posture][ADR-039]].

- Everything tangled from =config.org= is expected *identical* on every host:
  =init.el=, =packages.el=, =config.el=, =~/.bashrc=, =~/.inputrc=,
  =~/.gitconfig=, =~/.local/bin/{pass-backup,emacs-rebuild,firefox-chrome-install,emacs-magnet,desktop-install}=,
  =~/.local/share/applications/{org-protocol,emacs-magnet,emacs-mailto}.desktop=
  and =firefox/{user.js,userChrome.css,userContent.css}=. No
  =system-name= branching, no per-host config file, no per-host branch.
- Where a tangled file's *destination* is host-dependent — the Firefox profile
  path, [[id:adr-firefox-chrome-layer][ADR-043]] — the file itself stays identical and a tangled resolver
  script finds the path at run time. The host-specificity lives in the
  resolver, never in the content.
- A value that must vary by host takes an *environment-variable override with a
  working default* (the shape =PASS_BACKUP_DIR= has). A hardcoded absolute path
  that cannot be overridden is guarded so its absence on another host is a
  non-event, not a mystery.
- *Every documented fact about =$HOME= state, installed binaries, or credentials
  names its host.* "Installed", "verified", "gone" and "DONE" are meaningless
  without one. Repository facts and tangled output are host-independent by
  construction and need no qualifier.

The rule exists because its absence produced a wrong diagnosis: absent
credentials on the desktop were recorded as state that had *vanished*, when they
had only ever existed on the laptop. See
[[id:inv-homedir-state-loss][inventory.org]] for that correction.

* State outside the repository
:PROPERTIES:
:ID:       std-external-state
:END:

Some things this configuration depends on cannot live in it: a Firefox profile
directory whose path differs per machine, a font file, a line in
=~/.config/mimeapps.list=. They are legitimate, and each one is a liability of
the same specific kind.

*Anything outside this repository that the configuration depends on gets four
things.* Not three:

1. *A declaration in =config.org=.* What is wanted, named once, in the file that
   is the source of truth for everything else. =+my/font-families= and
   =+my/scheme-handlers= are the shape.
2. *An idempotent installer* that makes the declaration true and is safe to
   re-run. Tangled, like everything else. It prints every path it resolved, so
   "which thing was this actually going to" is never a question answered by
   guessing.
3. *A =--check= mode* that changes nothing and exits non-zero when reality has
   drifted from the declaration. Report-only, always: a checker that repairs
   things cannot be run to find out whether repair is needed.
4. *A line in the startup check*, =+my/external-state-checks=. A =--check= that
   nobody runs is a tool to be remembered, which is the failure it was built to
   end.

Miss any one and the whole thing degrades. A declaration without an installer is
a wish. An installer without a =--check= only works when you already suspect the
problem. A =--check= nothing runs is a script you will rediscover, after the
symptom, while looking for something else.

The rule exists because the failure mode is *silence*, and silence in the wrong
place. None of these things error when they drift. The Firefox profile goes
stale and a customisation appears not to take. A font is missing and
=+my/font-families= quietly falls through to its next entry, so the screen is
merely a little unlike what the configuration says. A scheme association is
taken over and the click simply goes somewhere else. In every case the symptom
surfaces in an application that is not at fault, which is the most expensive
possible place to start looking.

Three worked examples, and the history is the argument. =firefox-chrome-install=
([[id:adr-firefox-chrome-layer][ADR-043]]) came first and established the shape.
[[id:adr-font-roles][ADR-044]] then installed five font families by hand and left
nothing naming them; [[id:adr-org-protocol-capture][ADR-045]] added a scheme
association the same way, and noted that a third instance should produce a rule
rather than a fourth fix. Surveying for that third instance found two *older*
ones nobody had noticed — a hand-written =emacs-magnet= script that
[[id:adr-torrent-transmission][ADR-030]] depended on and never tangled, and four
=mimeapps.list= associations pointing at a browser that has never been installed
on this machine. =desktop-install= ([[id:adr-desktop-install][ADR-046]]) closed
those, and this rule exists so the next one is noticed when it is created rather
than two ADRs later.

Two things the rule deliberately does *not* demand. An installer never acquires
what needs a password — =apt= packages are *reported*, with the command to run,
because a script that sometimes stops for a password is worse than one that
never does. And an installer never deletes: what legitimately lives in a font
directory or a browser profile is not knowable from inside a script.

What is *not* covered, so this is not read as a mandate to track everything: state
a person is meant to change by hand and this configuration has no opinion about.
Firefox's toolbar layout, its compact-density choice, reader mode's font-type
toggle, browser bookmarks. [[id:adr-firefox-chrome-layer][ADR-043]] and
[[id:adr-font-roles][ADR-044]] both chose deliberately to leave those alone, and
pinning them would reverse a decision rather than implement one. The test is
whether the configuration *depends* on the value, not whether it could reach it.
