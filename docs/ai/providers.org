* Store status — lost 2026-09-14, rebuild pending
:PROPERTIES:
:ID:       providers-store-status
:END:

*The store on this host is gone and cannot be recovered.* On 2026-09-14 the
passphrase for the desktop GPG key =4F6F02436717EE9B823369EAE2F99AE2D3BDF9E1=
(generated 2026-08-30) was lost. All three entries were encrypted to that key
alone. A GPG private key without its passphrase has no reset path, so
=api/anthropic=, =api/openai= and the Google OAuth client entry are
unreadable — not misconfigured, not misnamed, unreadable.

=~/.local/bin/pass-backup= existed to prevent exactly this and had never been
run: =/data/backups/pass/= does not exist. The only backup that did exist was a
hand-made =password-store-2026-09-08.tar= on a USB stick holding the encrypted
store and no key, which is no backup at all. See
[[id:adr-credential-backup-enforced][ADR-048]] for the decision that came out
of it, and =docs/pass-rebuild.md= for the step-by-step rebuild.

Current disposition, all deliberate and all pending the rebuild:

- The dead store is archived at =~/.password-store.dead-2026-09-14=.
  =~/.password-store= no longer exists, so =my/pass-check-store= warns at every
  startup and gptel's two backends resolve against nothing.
- The dead key is still in the keyring. It shares a UID with whatever key
  replaces it, so every command in the rebuild takes an explicit fingerprint
  rather than matching on =mrniceguyjames@gmail.com=.
- Neither is recoverable; both are kept only until the replacement is confirmed
  working.

*Which passphrase was lost is not established.* If it was the desktop key's,
the laptop store is intact and its key (=859AF991C9EA4396=) still opens the USB
tarball — the values can be carried across by hand with no re-issuing. If it
was the laptop key's, the values are gone and all three credentials must be
re-issued and the old ones revoked. =docs/pass-rebuild.md= step 0 is the check
that settles it, and it must be run before anything is re-issued.

*The two defects this section used to track are moot.* The rebuilt store's
=mail/oaut2-google-client= typo and its missing =client_id= line died with the
store. They are recorded here only so a future reader does not go looking for
them: the rebuild creates =mail/oauth2-google-client= correctly from the start,
per the shape below.

*The pending laptop-to-desktop USB transfer is cancelled.* It assumed a working
desktop key to name as a second recipient and a desktop store worth replacing;
neither exists. =docs/pass-usb-transfer.md= has been replaced by
=docs/pass-rebuild.md=.

One question that survives the loss, because it was settled from source rather
than guessed: the client-id *field name* is =client_id=. =+pass-get-field= is a
=defalias= onto =auth-source-pass-parse-entry=, which treats line 1 of an entry
as the secret and splits every later line at its first colon into a trimmed
=key: value= pair. =config.org= tries =client_id= / =client-id= / =login= /
=user= in order, so any of the four resolves.

Update the Status column above when the entries are rebuilt, and again when
they are exercised through gptel — not merely when they are present.

* Model policy — implemented (Phase 4)
:PROPERTIES:
:ID:       providers-models
:END:

Previous state hardcoded =gptel-make-openai= only, with model list
=(gpt-4o-mini gpt-4o)= — both superseded as of 2026-07-20.

Now: =:models= is omitted on both =gptel-make-anthropic= and =gptel-make-openai=
calls. Source inspection of gptel 0.9.9.5 (=gptel-anthropic.el=/=gptel-openai.el=)
confirmed both constructors default =:models= to gptel's own maintained registry
(=gptel--anthropic-models=/=gptel--openai-models=) when the keyword is omitted —
so the available model list tracks upstream automatically instead of being
hardcoded here and going stale. Live-verified: the Anthropic registry includes
=claude-sonnet-5=/=claude-opus-4-8=/=claude-haiku-4-5-20251001=/=claude-fable-5=;
the OpenAI registry includes the current =gpt-5.x=/=o3=/=o4= generation.

Default backend/model: Anthropic / =claude-sonnet-5= (matches cloud-first +
"best engineering workflow, not cheapest" per [[id:std-cloud-first][standards.org]]). OpenAI
configured as a secondary backend, selectable via =gptel-menu= (=SPC o l m=, [[id:adr-llm-module-owns-ai-keys][ADR-028]]).
Gemini not configured — explicit user decision, not an oversight.
