* Store status, 2026-08-30
:PROPERTIES:
:ID:       providers-store-status
:END:

Found during the Phase 7 audit ([[id:roadmap-phase-7][roadmap]]): the password
store this whole document describes is *gone*. Not misconfigured — absent.

- No =pass= binary anywhere on the system, and no =pass= apt package installed.
- No =~/.password-store=, no =~/.local/share/password-store=, and
  =PASSWORD_STORE_DIR= unset.
- =~/.gnupg/private-keys-v1.d/= is empty, directory dated 2020-06-06. There is
  no GPG secret key, so even a recovered store could not be decrypted. The only
  key in the public keyring belongs to a Debian developer and was presumably
  imported for package verification.
- No backup of a store was found anywhere under =/home/james=.

Consequence: =config.org='s =+pass-get-secret= calls for =api/anthropic= and
=api/openai= fail, so gptel's Anthropic and OpenAI backends do not work. This
was plausibly unnoticed because agentic work goes through claude-code-ide.el,
which uses the Claude CLI's own subscription login and never touches =pass=.
=+pass-get-field= for =mail/oauth2-google-client= fails the same way, which is a
second, independent reason [[id:adr-calendar-org-gcal][ADR-025]]'s calendar work
has not been able to proceed.

Rebuilding is not a recovery — there is nothing to decrypt. It means a new GPG
key, =pass init=, and re-entering each secret from its provider's dashboard.
Those steps are interactive by nature (a passphrase, and secret values) and are
deliberately not scripted. =pass= and =pass-otp= are installed; the remaining
sequence is recorded as a checklist in PROJECT.org §7.7, which also records the
one detail that had been an open question since [[id:adr-calendar-org-gcal][ADR-025]]: the client-id field
name is =client_id=, settled from =auth-source-pass= source rather than guessed.

When the store is rebuilt, update the Status column above rather than leaving
this section to contradict it.

Requirements carried over from [[id:std-credentials][standards.org]]: no secret values in git, in Org
Babel results, in command transcripts, or in =CLAUDE.md=/=AGENTS.md=/prompts/logs.
Held to throughout Phase 4 — every credential check during implementation
verified only string type/length, never content.

* Model policy — implemented (Phase 4)
:PROPERTIES:
:ID:       providers-models
:END:

Previous state hardcoded =gptel-make-openai= only, with model list
=(gpt-4o-mini gpt-4o)= — both superseded as of 2026-07-20.

Now: =:models= is omitted on both =gptel-make-anthropic= and =gptel-make-openai=
calls. Source inspection of gptel 0.9.9.5 (=gptel-anthropic.el=/=gptel-openai.el=)
confirmed both constructors default =:models= to gptel's own maintained registry
(=gptel--anthropic-models=/=gptel--openai-models=) when the keyword is omitted —
so the available model list tracks upstream automatically instead of being
hardcoded here and going stale. Live-verified: the Anthropic registry includes
=claude-sonnet-5=/=claude-opus-4-8=/=claude-haiku-4-5-20251001=/=claude-fable-5=;
the OpenAI registry includes the current =gpt-5.x=/=o3=/=o4= generation.

Default backend/model: Anthropic / =claude-sonnet-5= (matches cloud-first +
"best engineering workflow, not cheapest" per [[id:std-cloud-first][standards.org]]). OpenAI
configured as a secondary backend, selectable via =gptel-menu= (=SPC o l m=, [[id:adr-llm-module-owns-ai-keys][ADR-028]]).
Gemini not configured — explicit user decision, not an oversight.
