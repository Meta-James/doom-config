* Store status — absent on this host, rebuilt 2026-08-30
:PROPERTIES:
:ID:       providers-store-status
:END:

The Phase 7 audit recorded the password store this document describes as
*gone* — no =pass= binary, no =~/.password-store=, =PASSWORD_STORE_DIR= unset,
and an empty =~/.gnupg/private-keys-v1.d/= dated 2020-06-06. Two corrections
have landed on that reading since, and both matter more than the original
finding.

*It was never on this host.* Nothing was lost. The Phase 3 credential work
happened on James's laptop, where the store, the GPG key and the mail stack
still live; this desktop (=PsychedPC=) simply never had them. The real defect
was documentation that described one host while being read on another — see
[[id:adr-multi-host-posture][ADR-039]] for the multi-host posture that came out
of it, and =docs/inventory.org='s =inv-homedir-state-loss= section.

*A store now exists here, rebuilt rather than transferred.* On 2026-08-30 a new
GPG key was generated on this desktop (ed25519 primary with a cv25519 encryption
subkey, fingerprint =4F6F02436717EE9B823369EAE2F99AE2D3BDF9E1=), =pass init= run
against it, and all three entries re-entered from their provider dashboards.
=~/.password-store= holds =api/anthropic=, =api/openai= and the Google OAuth
client entry. The store is encrypted to the desktop key alone — the laptop key is
not a recipient.

Two defects in the rebuilt store, outstanding as of 2026-09-04 and James's own to
fix (an agent never handles the values):

1. *Entry-name typo.* The store holds =mail/oaut2-google-client=; =config.org=
   asks for =mail/oauth2-google-client=, both at its three =+pass-get-field= call
   sites and in =my/pass-check-store='s expected-entry list. So the startup guard
   warns and org-gcal never finds a client. The fix is =pass mv= — a rename, with
   no value decrypted or printed.
2. *That entry has no =client_id= line.* It is a single line, the secret only.
   =+pass-get-field= needs =client_id: <id>.apps.googleusercontent.com= as line 2
   before it can resolve a client id. The fix is =pass edit=.

Unverified beyond those two: both =api/*= entries are two lines and shorter than
these providers' keys normally run, which is the shape of a paste that wrapped.
Confirming that means one request per provider reporting *HTTP status only*,
never the value, and it needs James's say-so first, because it puts a live key on
the network.

*A transfer is still pending, and supersedes the rebuild.* PROJECT.org §7.7
records moving the laptop's store here on an encrypted USB archive; James intends
to run its laptop half. The transferred store carries the entry names and fields
Phase 3 actually used, so it may resolve both defects above on its own — check
them against the transferred store rather than fixing the store twice.

One question this closes for good: the client-id *field name* is =client_id=,
settled from =auth-source-pass= source rather than guessed. =+pass-get-field= is
a =defalias= onto =auth-source-pass-parse-entry=, which treats line 1 of an entry
as the secret and splits every later line at its first colon into a trimmed
=key: value= pair. =config.org= tries =client_id= / =client-id= / =login= /
=user= in order, so any of the four resolves.

Update the Status column above when the entries are exercised through gptel, not
merely when they are present.

Requirements carried over from [[id:std-credentials][standards.org]]: no secret values in git, in Org
Babel results, in command transcripts, or in =CLAUDE.md=/=AGENTS.md=/prompts/logs.
Held to throughout Phase 4 — every credential check during implementation
verified only string type/length, never content.

* Model policy — implemented (Phase 4)
:PROPERTIES:
:ID:       providers-models
:END:

Previous state hardcoded =gptel-make-openai= only, with model list
=(gpt-4o-mini gpt-4o)= — both superseded as of 2026-07-20.

Now: =:models= is omitted on both =gptel-make-anthropic= and =gptel-make-openai=
calls. Source inspection of gptel 0.9.9.5 (=gptel-anthropic.el=/=gptel-openai.el=)
confirmed both constructors default =:models= to gptel's own maintained registry
(=gptel--anthropic-models=/=gptel--openai-models=) when the keyword is omitted —
so the available model list tracks upstream automatically instead of being
hardcoded here and going stale. Live-verified: the Anthropic registry includes
=claude-sonnet-5=/=claude-opus-4-8=/=claude-haiku-4-5-20251001=/=claude-fable-5=;
the OpenAI registry includes the current =gpt-5.x=/=o3=/=o4= generation.

Default backend/model: Anthropic / =claude-sonnet-5= (matches cloud-first +
"best engineering workflow, not cheapest" per [[id:std-cloud-first][standards.org]]). OpenAI
configured as a secondary backend, selectable via =gptel-menu= (=SPC o l m=, [[id:adr-llm-module-owns-ai-keys][ADR-028]]).
Gemini not configured — explicit user decision, not an oversight.
