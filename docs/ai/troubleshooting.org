* RESOLVED: =SPC a= reclamation was dead code, never executed
:PROPERTIES:
:ID:       tshoot-dead-keybind-code
:END:
:LOGBOOK:
- Resolved [2026-07-20 Mon], during [[id:adr-ai-leader-namespace][ADR-003]] implementation
:END:

The original =SPC a= reclamation (unbinding =embark-act=, adding an "apps"
prefix with AI commands under =SPC a i=) was wrapped in =(after! doom-keybinds
...)=. =doom-keybinds= was never a real Emacs feature — grepped the entire
Doom core (=~/.config/emacs/lisp=) and the full split-out module source
(=~/.config/emacs/sources/doom+/modules=) for any =(provide 'doom-keybinds)=:
zero matches. =after!= expands to something like =with-eval-after-load=; it
waits forever for a =provide= that never happens. This block never ran, in any
session, ever.

*Practical consequence*: Embark's default =SPC a= binding was presumably still
live the entire time this config was in use, and the old AI commands under
=SPC a i= were only reachable via =M-x=, never via the documented keybinding.

*Fix*: removed the =after!= wrapper entirely. Plain =(map! :leader "a" nil)=
followed by a real =(map! :leader (:prefix ("a" . "AI") ...))= works correctly
without any guard, because =config.el= loads after Doom's default-bindings
module has already run — there's nothing to "wait for."

*Takeaway*: an =after!= (or =with-eval-after-load=) block on a feature symbol
that is never independently verified to exist is silently inert, not an error.
If a keybinding or config block "should be working" but demonstrably isn't,
check whether its guard condition (feature symbol, hook, mode) is real before
assuming the body itself is wrong.

* Technique: validating config changes without touching the user's live session
:PROPERTIES:
:ID:       tshoot-daemon-validation
:END:

Doom only loads =config.el=/=packages.el=/=init.el= changes at Emacs startup —
there's no live-reload for structural changes. Two failed approaches before
finding one that works, kept here so the next validation pass doesn't repeat
them:

- Plain =emacs --batch --eval '...'= *does* auto-load Doom's core (since
  =~/.config/emacs= is the default =user-emacs-directory=), but Doom detects
  =noninteractive= and skips loading the user's =config.el= entirely (it's
  treated as UI-only). A batch run reporting "no errors" proves nothing about
  =config.el= correctness — nothing in it actually ran.
- =~/.config/emacs/bin/doom run --eval '(...)'= and
  =~/.config/emacs/bin/doom emacs --batch --eval '(...)'= both fail with a
  shell-level =Syntax error: "(" unexpected= — the =bin/doom= wrapper script
  mishandles arguments containing parentheses when invoked this way from
  another shell. Use the absolute =emacs= binary directly instead of routing
  through =bin/doom= for anything beyond =sync=/=doctor=/=upgrade=/=build=.

*What actually works*: start a fully interactive Doom instance as a named,
isolated daemon — =emacs --daemon=some-test-name= — which loads =config.el=
exactly as a real interactive session would (confirmed: it even started the
Copilot language server, which only happens via a =prog-mode= hook). Then
inspect live state with
=emacsclient --socket-name=some-test-name --eval '(...)'=, and clean up with
=emacsclient --socket-name=some-test-name --eval '(kill-emacs)'=. Always use a
distinct =--socket-name= — the user's own day-to-day Doom session runs as a
persistent daemon on the *default* socket (discovered via =ps aux= showing an
=/usr/bin/emacs --daemon= process pre-dating this project), and it must never
be queried, reloaded, or killed as a side effect of validation.

Reminder for every future phase: that long-running daemon does not
automatically pick up config changes. After any phase that changes
=init.el=/=config.el=/=packages.el=, tell the user their live session needs a
restart to actually get the changes — don't assume it happened.

* OPEN: literal-tilde =$PATH= entry breaks non-interactive =doom= invocation
:PROPERTIES:
:ID:       tshoot-path-tilde
:END:

=$PATH= contains =~/.config/emacs/bin= as a literal, unexpanded string (confirmed
via =echo $PATH=, 2026-07-20). Interactive bash resolves =doom= anyway via its own
tilde-aware command hashing (=type doom= succeeds), but any subprocess doing a raw
=execvp= PATH search fails: e.g. =timeout doom doctor= errored with "No such file
or directory" even though =doom= itself was reachable in the same shell a moment
earlier.

*Impact*: anything that shells out to =doom= non-interactively — including a
future agent asked to run =doom sync=/=doom doctor= as part of its own workflow —
may silently fail to find the command. Workaround used throughout this project:
always invoke via the absolute path, =~/.config/emacs/bin/doom=.

*Not yet fixed* — this is a shell-profile issue (wherever =$PATH= is being
assembled with an unexpanded =~=), outside this repo's scope unless it starts
blocking a real agent workflow in Phase 6, at which point it should be fixed at
the shell-profile level, not worked around again in Elisp.

* OPEN: agent's Bash-tool checks reported installed packages as missing
:PROPERTIES:
:ID:       tshoot-agent-shell-system-state
:END:

During [[id:adr-app-launcher][ADR-020]], the agent ran =which wmctrl xdotool= (reported both
missing), then separately =dpkg -s libpoppler-glib-dev= (reported not
installed) and told the user both needed installing. The user directly
corrected this afterward: both packages were already installed on the real
machine at the time of *both* checks. A follow-up =command -v xdotool=/
=dpkg -s xdotool= *did* find =xdotool= correctly — inconsistent with the
first =which= check on the same machine, same session.

The agent's first guess — "sandboxed shell, restricted =$PATH="" — does not
hold up: the user stated plainly it has nothing to do with =PATH=, and the
later, correct =xdotool= check ran with the same (default, non-
=dangerouslyDisableSandbox=) invocation style as the first, wrong one. No
sandbox-vs-not pattern actually distinguishes the wrong checks from the
right ones.

*Impact*: a future agent cannot treat its own Bash-tool =dpkg=/=which=/
=command -v= output as ground truth for whether something is installed on
this machine — at least not without corroboration. Concretely seen so far:
both a false-negative (=xdotool=, =which=) and a reproducible-but-still-wrong
negative (=libpoppler-glib-dev=, =dpkg -s=, which normally doesn't produce
false negatives — it reads a local database, not =PATH=).

*Not yet fixed, cause not determined.* Until root-caused, treat any "X is
not installed" conclusion reached solely via the agent's own shell as
provisional: prefer asking the user directly, or checking through a live
connection to the user's actual session (e.g. the =mcp__emacs-tools__*=
MCP tools, which do reach the user's real running Emacs — confirmed via
=claude-code-ide-mcp-project-info= returning the real project/buffer) over
re-running more agent-shell commands that may be checking the wrong thing.

* OPEN: =org-agenda-list= hangs a frame-less headless daemon
:PROPERTIES:
:ID:       tshoot-agenda-headless-daemon-hangs
:END:
:LOGBOOK:
- Found [2026-08-23 Sun], while testing Phase 5's agenda-open sync hook ([[id:adr-calendar-org-gcal][ADR-025]])
:END:

In a disposable =emacs --daemon=<name>= started against this config, an
=emacsclient --eval "(org-agenda-list)"= never returns — the client times out
and every subsequent =--eval= against that daemon also hangs, so the daemon
has to be killed by PID. The Emacs process itself stays in state =S= with no
=gpg=/=pinentry= child, which points at a blocking minibuffer read rather than
a stuck subprocess.

*Not root-caused.* What is established is what it is *not*: it reproduces with
=org-agenda-mode-hook='s org-gcal entry removed, and with =org-agenda-files=
pointed at an empty scratch directory instead of =~/org=. So it is neither the
calendar sync hook nor anything about the real agenda files — it is the
frame-less daemon itself, in the same family as [[id:tshoot-ghostel-needs-x-frame][the ghostel entry below]].

*Takeaway for future sessions*: the isolated-headless-daemon pattern is still
the right way to verify agenda-adjacent *wiring* — hooks attached, variables
set, bindings resolved, =(require ...)= clean — and that is exactly how Phase
5's config was checked. It cannot verify agenda *behavior*. Don't call
=org-agenda-list= (or anything that opens the agenda) in a frame-less daemon,
and don't read a hang there as evidence about the code under test. If agenda
behavior genuinely needs testing, attach a real X frame first, the way the
ghostel entry describes.

* CONFIRMED: Doom's tree-sitter module grammar-install advice is broken on Emacs 30.x
:PROPERTIES:
:ID:       tshoot-treesitter-confirmed
:END:
:LOGBOOK:
- Confirmed [2026-07-20 Mon], during [[id:adr-claude-code-ide-install][ADR-008]] verification (Phase 6)
:END:

Upstream issue =doomemacs/doomemacs#8578= reports the =:tools tree-sitter=
module advising a function that doesn't exist on Emacs 30.x, corrupting the
advice system and breaking interactive grammar installation. Reproduced
directly on this machine (isolated headless daemon, read-only inspection):

- =~/.config/emacs/sources/doom+/modules/tools/tree-sitter/config.el= (lines
  ~108-114) has a version-conditional: on Emacs 30+, it calls a single
  =defadvice!= with *two* =:around= targets —
  =treesit-install-language-grammar= and =treesit--build-grammar=.
- =(fboundp 'treesit-install-language-grammar)= → t (exists; advice attached
  successfully, confirmed via =advice-member-p=).
- =(fboundp 'treesit--build-grammar)= → *nil* — this function does not exist
  on Emacs 30.1. This is the exact defect the upstream issue describes.
- Separately, and independently of this bug: *zero* tree-sitter grammars (for
  any language, not just Python/Elisp) were installed anywhere on this
  machine before this check — =treesit-language-available-p= returned nil for
  both =python= and =elisp=, and no =libtree-sitter-*.so= files exist under
  =~/.config/emacs/.local/etc/tree-sitter= or elsewhere on the system.

*Impact*: claude-code-ide.el's =claude-code-ide-mcp-treesit-info= MCP tool
(see [[id:adr-claude-code-ide-install][ADR-008]]) has no working grammars to draw on right now, for two
independent reasons — the confirmed upstream bug, and the separate fact that
grammar installation was never attempted on this machine at all.

*Not fixed* — deliberately did not attempt a real grammar install to see it
fail, since that would mean fetching and compiling third-party C source
without prior sign-off, for a test whose outcome is already evidenced by the
=fboundp= check above. Workarounds, in order of preference:
1. Wait for upstream to fix the =doomemacs/doomemacs#8578= advice.
2. Manually build the needed grammar(s) via the =tree-sitter= CLI directly
   (bypassing Doom's automatic installer entirely) and place the resulting
   =.so= file(s) in =(doom-profile-data-dir t "tree-sitter")=, matching where
   Doom's own hook adds to =treesit-extra-load-path=.
3. Patch the local module copy to split the =defadvice!= into two calls (one
   per target function), guarding the =treesit--build-grammar= one with
   =(fboundp 'treesit--build-grammar)= — a small, local, easily-reverted fix,
   not proposed unprompted since it edits Doom's own module source rather
   than this repo's files.

* RESOLVED: vterm's native module was never compiled, hanging any headless =(require 'vterm)=
:PROPERTIES:
:ID:       tshoot-vterm-module
:END:
:LOGBOOK:
- Resolved [2026-07-20 Mon], during the Phase 6 live smoke test ([[id:adr-claude-code-ide-install][ADR-008]])
:END:

Attempting to launch a claude-code-ide.el session (vterm backend) in a
headless test daemon hung indefinitely — not just slow, genuinely
unresponsive to even trivial evals afterward (=(+ 1 1)= timed out). Bisected
by testing each step of =claude-code-ide--start-session= individually in
fresh daemons rather than guessing: =claude-code-ide-mcp-server-ensure-server=
and =claude-code-ide--display-buffer-in-side-window= both returned instantly
in isolation; =claude-code-ide--terminal-ensure-backend= was the one that
hung.

Root cause: that function calls =(require 'vterm nil t)=. No
=vterm-module.so= existed anywhere under
=~/.config/emacs/.local/straight/build-30.1/vterm/= — only the C source. On
first load with no compiled module, =vterm.el= checks
=vterm-always-compile-module= (defaults to =nil=) and *asks for interactive
confirmation* before compiling. Over a headless =emacsclient --eval= with no
attached terminal or frame, that confirmation prompt has nowhere to go and
blocks the entire Lisp thread forever — every subsequent =emacsclient --eval=
call queues behind it and also appears to hang, which is what made this look
like a total daemon lockup rather than one blocked function.

*This would have hit the user's real session too* — the first time either
=my/project-vterm= or claude-code-ide.el actually tried to use vterm
interactively, they'd have hit the same confirmation prompt (harmlessly, since
their session has a real terminal/frame to show it on and they could just
answer yes).

*Fix*: ran vterm's own documented build recipe directly instead of trying to
trigger/bypass the confirmation prompt inside another fragile headless eval:
#+BEGIN_SRC sh
cd ~/.config/emacs/.local/straight/build-30.1/vterm
mkdir -p build && cd build
cmake -G 'Unix Makefiles' ..
make
#+END_SRC
This fetched and built =libvterm= (no system copy was installed) and produced
=vterm-module.so= in that build directory — the same shared location every
Doom Emacs instance on this machine reads from, including the user's real
daemon. Confirmed fixed: =(require 'vterm)= in a fresh headless daemon
returned instantly afterward, and the actual smoke-test session launched
successfully on the next attempt.

*Takeaway*: when a headless daemon appears to hang on ANY eval (not just the
one you just ran), suspect a blocked interactive prompt from something loaded
during that call, not a crashed or infinite-looping daemon — kill it, then
bisect the triggering call's internal steps individually in fresh daemons
with short timeouts to find which one actually blocks, rather than re-running
the same monolithic call and waiting out the same timeout repeatedly.

* RESOLVED: real Emacs daemon's =PATH= (systemd-launched) lacked =~/.local/bin=, so =claude= wasn't found
:PROPERTIES:
:ID:       tshoot-daemon-path-systemd
:END:
:LOGBOOK:
- Confirmed and fixed [2026-07-21 Tue], during Phase 7, reported directly by
  the user as "Claude Code CLI not on PATH"
:END:

Distinct from [[id:tshoot-path-tilde][the literal-tilde =$PATH= issue]] above — this is a different
mechanism with the same symptom class (a subprocess can't find a binary that
the user's interactive shell can).

*Diagnosis*: the user's real Emacs daemon (=ps= showed =/usr/bin/emacs
--daemon=, PPID = =/usr/lib/systemd/systemd --user=, started 2026-07-20
17:56:39) was launched by the systemd user session, not from a login shell.
=/proc/<pid>/environ= showed its =PATH= as
=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin:/snap/bin=
— systemd's bare default, missing =/home/james/.local/bin= entirely (where
=claude= lives, per [[id:docs-inventory][inventory.org]]/Phase 0 discovery). Any subprocess or
MCP tool launched from that daemon (including claude-code-ide.el trying to
find the =claude= CLI) inherits this minimal PATH and fails to find it, even
though the CLI is perfectly reachable from any interactive shell.

*Why earlier structural verification didn't catch this*: [[id:adr-claude-code-ide-install][ADR-008]]'s Phase 6
verification tested CLI detection in disposable =emacs --daemon=doom-phaseN-test=
instances spawned directly from an interactive shell in an agent session —
those inherit a full, correct =PATH= and passed cleanly. That was real
verification of the detection *logic*, but not of the user's actual
long-running daemon's *environment*, which is provisioned differently
(systemd, not a shell). The gap wasn't a code bug; it was an environment
difference between the test rig and the real target.

*Root cause, more precisely*: Doom ships a dedicated fix for exactly this
class of problem — =doom sync --env= scrapes the user's real interactive
shell environment (via =$SHELL -ic env=) into a profile-scoped file
(=<profile-dir>/init.d/05-doom-env.load.el=), which Doom's init sequence
loads automatically on every subsequent =doom sync=/Emacs startup, and which
can be reloaded into an *already-running* session with =M-x doom/reload-env=
(no restart needed — see =~/.config/emacs/lisp/lib/config.el=). This had
simply never been run on this machine: no =05-doom-env.load.el= existed
anywhere under =~/.config/emacs/.local=. A stray, unrelated =~/.config/emacs/.local/env=
file did exist (dated 2026-03-24, from some earlier one-off =doom env=
invocation using an older/different output convention) but nothing loads
that path — it was inert.

*Fix*:
#+BEGIN_SRC sh
~/.config/emacs/bin/doom sync --env
#+END_SRC
Regenerated =05-doom-env.load.el= with the current shell's real =PATH=
(confirmed via =grep= on the generated file: includes
=/home/james/.local/bin=, and — unlike the stale 2026-03-and file — no
literal-tilde entry this time). This alone fixes every *future* Emacs start
(daemon or otherwise). To apply it to the *already-running* daemon without
restarting it (preserving open buffers/frames), the user runs =M-x
doom/reload-env= once in their live session; restarting Emacs works too but
is unnecessary. The agent deliberately did not run this against the user's
live daemon itself (via =emacsclient --eval=) — same standing caution as
everywhere else in this project about not touching the user's real running
session beyond read-only inspection.

*Takeaway*: a headless/disposable test daemon spawned from an agent's own
shell is not equivalent to the user's actual long-running daemon if that
daemon was started by something other than an interactive shell (systemd
user session, a display manager, =emacs --daemon= in an init script, etc.).
"CLI detection works" verified in an isolated test daemon is evidence about
the *code path*, not proof the *user's actual daemon* will behave the same —
worth checking =ps -o pid,ppid,cmd= for the real daemon's parent and
=/proc/<pid>/environ= for its actual PATH before treating a structural pass
as equivalent to a live-environment pass.

* CLARIFIED: "file references open from Emacs" was never a click-a-link feature
:PROPERTIES:
:ID:       tshoot-file-refs-mis-scoped
:END:
:LOGBOOK:
- Clarified [2026-07-21 Tue], during Phase 9 acceptance testing — user tried
  clicking file references in a live claude-code-ide.el session and found
  nothing was clickable
:END:

The Phase 9 test plan asked the user to check whether a file reference
appearing in the agent's chat/vterm output could be clicked to open it in
Emacs. It couldn't — but source inspection shows this was never a real
feature to begin with, not a regression or bug:

- =claude-code-ide.el='s =openFile= handler
  (=claude-code-ide-mcp-handle-open-file= in
  =claude-code-ide-mcp-handlers.el=, registered against the MCP tool name
  =openFile=) is an *MCP tool the running =claude= CLI process calls at its
  own discretion* — Emacs exposes it as a capability the agent can invoke,
  the agent decides when. There is no code path from "text the agent
  printed" to "clickable button" anywhere in this package.
- vterm itself (checked its elisp source) has no OSC-8/hyperlink handling
  that would make arbitrary terminal text clickable either. Nothing on
  either side of the integration implements the behavior the original
  Phase 6 acceptance-test wording assumed.
- The underlying mechanism *does* work, just not via clicking: it's the same
  =find-file= plumbing behind claude-code-ide.el's automatic Ediff diff view
  (=claude-code-ide-use-ide-diff=), already live-verified in Phase 7 — when
  the agent edits a file, Emacs opens it for the diff review, driven by the
  agent's own tool call, not a user click.

*Takeaway*: the original acceptance-test wording ("file references open from
Emacs") conflated two different things — a user-facing clickable-link
affordance (doesn't exist) and an agent-initiated file-open capability (does
exist, already exercised via Ediff). Write acceptance criteria against a
verified mechanism, not an assumed one — this one should have been checked
against source before being handed to the user to test by hand.

* RESOLVED: poisoned =05-doom-env.load.el= caused "Transcript saving is off", recurring every reboot
:PROPERTIES:
:ID:       tshoot-claude-env-leak
:END:
:LOGBOOK:
- Resolved [2026-08-11 Tue], reported directly by the user as "Transcript
  saving is off" recurring identically after every reboot, in a
  claude-code-ide.el session
- Live-verified [2026-08-11 Tue]: user opened a real claude-code-ide.el
  session in their live daemon (after the =config.el= strip was applied to
  it, see [[id:adr-strip-claude-env-vars][ADR-013]]'s LOGBOOK) and confirmed it worked, no "Transcript
  saving is off".
:END:

Same underlying mechanism as [[id:tshoot-daemon-path-systemd][tshoot-daemon-path-systemd]] above (=doom sync
--env='s cache, =05-doom-env.load.el=, loaded unconditionally on every Emacs
startup), different poison: on 2026-08-10 that command was run from *inside
an active Claude Code CLI subprocess shell*, so the scrape captured and
permanently baked in that shell's ephemeral, subprocess-only Claude Code
identity vars (=CLAUDECODE=1=, =CLAUDE_CODE_SESSION_ID=,
=CLAUDE_JOB_DIR=, =CLAUDE_PID=, =CLAUDE_CODE_CHILD_SESSION=1=,
=CLAUDE_CODE_ENTRYPOINT=cli=, =AI_AGENT=) belonging to a session/job that had
already exited. Every subsequent Emacs startup — including after reboot —
reloaded this cache, so every =claude= process launched from Emacs afterward
inherited a dead session's identity instead of a fresh one. Confirmed live,
in the diagnosing session itself: its own =CLAUDE_JOB_DIR= env var pointed at
the stale, already-exited job directory from the poisoned file (not its own,
different, real session ID) — and that job directory's =exit-cause=/
=exit-detail= read =exit_with_message= / "No conversation found to
continue".

Confirmed via Anthropic's own docs
([[https://code.claude.com/docs/en/env-vars]]) that =CLAUDECODE=/
=CLAUDE_CODE_CHILD_SESSION= are documented as subprocess-only markers, never
meant to be inherited past that subprocess's lifetime, and that a process
seeing =CLAUDE_CODE_CHILD_SESSION=1= is "automatically excluded from
--resume, --continue, up-arrow history, and the claude agents list" —
matching the observed "No conversation found to continue" and almost
certainly the mechanism behind "Transcript saving is off" too. Confirmed via
GitHub issue =anthropics/claude-code#26190= this is a known bug class
(inherited =CLAUDECODE=/=CLAUDE_CODE_ENTRYPOINT= confusing a freshly-launched

connection, confirmed via =(frame-parameter nil 'window-system)= returning

always exist.

*Takeaway*: any future headless/disposable-daemon smoke test involving

* RESOLVED: dashboard silently replaced the Magit commit-message buffer
:PROPERTIES:
:ID:       tshoot-dashboard-stomps-commit-buffer
:END:
:LOGBOOK:
- Resolved [2026-08-20 Thu] — previous "Resolved" state (2026-08-18) was
  premature: the guard it added never actually worked, for a different
  reason than originally diagnosed. See second root-cause note below.
- Resolved [2026-08-18 Tue]
:END:

*Symptom*: committing via Magit, the frame that opened to edit the commit
message showed the dashboard instead. Pressing =q= (which buries/quits the
dashboard buffer) revealed the actual =COMMIT_EDITMSG= buffer underneath, as
if it had been open the whole time. Reliably reproducible on every commit,
not intermittent.

*Original root cause* (2026-08-18, incomplete): the 43b3bcc "Fixed
maximization bug on Ubuntu" commit (=config.el=) hooked
=server-after-make-frame-hook= to force the dashboard open on *every* client
frame emacsclient creates, via
=(run-with-timer 0.1 nil #'+dashboard/open (selected-frame))= — with no
guard for frames that were created to edit a specific file. Traced Emacs's
own =server.el= (=server-execute=): it calls =server-visit-files= and
=server-switch-buffer= to display the requested file *before*
=server-after-make-frame-hook= runs, so at hook time the frame is already
showing the right buffer. Fixed (69a66c2) by guarding the timer callback
with =(with-selected-frame frame (unless buffer-file-name (+dashboard/open
frame)))=.

*That fix never actually worked* — root-caused for real on 2026-08-20 by
reproducing against a live Emacs (instrumented =magit-commit-create= in a
scratch repo, with advice on =+dashboard/open= comparing state at the
failure point). Two things were wrong:

1. =server-execute='s ordering claim only holds for =server-visit-files=
   (which loads the buffer into memory) — it does *not* cover
   =server-switch-buffer= (which actually displays it in the frame's
   window). Reading the real source: =run-hooks
   'server-after-make-frame-hook= fires *before* =server-switch-buffer=, not
   after. So at hook time the frame's window is still showing whatever was
   there previously, not the new file — the original fix's premise was
   backwards.
2. The guard's own check compounded this: =(with-selected-frame frame
   (unless buffer-file-name ...))= reads =buffer-file-name= against
   *=current-buffer=*, and =select-frame= (which =with-selected-frame=
   expands to) does *not* sync =current-buffer= to the frame's selected
   window — only actually switching to a window's buffer does that. Live
   evidence: at the exact moment =+dashboard/open= ran, the frame's window
   was correctly showing =COMMIT_EDITMSG= (confirmed via
   =(buffer-file-name (window-buffer (frame-selected-window frame)))= →
   the real path), while bare =buffer-file-name= in that same timer
   callback read =nil= against an unrelated current buffer. The check was
   testing the wrong thing regardless of timing, so no delay would have
   fixed it.

*Real fix*: check the frame's selected window's buffer directly, never
=current-buffer=:
#+begin_src emacs-lisp
(unless (buffer-file-name (window-buffer (frame-selected-window frame)))
  (with-selected-frame frame
    (+dashboard/open frame)))
#+end_src
Verified live against a scratch git repo across three consecutive
=magit-commit-create= calls (the original bug's failure mode specifically
needed a *second* commit in the session, once =COMMIT_EDITMSG= already had
a live buffer to revisit) — =COMMIT_EDITMSG= stayed on screen at t+0.05
through t+0.5s on every attempt, no dashboard stomp.

*Takeaway*: any hook on =server-after-make-frame-hook= that unconditionally
takes over the frame's window is a landmine for every other feature that
opens files through emacsclient (with-editor/Magit here, but equally
=git rebase -i= or any other =$EDITOR=-via-emacsclient caller) — gate on
whether the frame already has something real displayed, not just on "a new
client frame was created". And more generally: =select-frame=/
=with-selected-frame= change which frame and window are *selected*, not
which buffer is *current* — never read =(buffer-file-name)= or other
current-buffer state as a proxy for "what's this frame showing"; go through
=(window-buffer (frame-selected-window FRAME))= explicitly. A live
reproduction beat re-reading the same (in this case wrong) source-tracing
argument a second time — don't trust a "traced the source" root cause
without a runtime check that actually observes the failure state.

:PROPERTIES:
:ID:       tshoot-claude-code-ide-json-rpc-error-uncaught
:END:
:LOGBOOK:
- Logged and patched [2026-08-21 Fri], hit at the start of an ordinary
  session (no unusual request in flight)
:END:

*Symptom*: an unprompted, uncaught error appeared in =*Messages*= at session
start: =error in process filter:
claude-code-ide-mcp-http-server--handle-post: peculiar error: -32601,
"Method not found"=. Nothing in this repo's own config triggered it — it
came from the vendored =claude-code-ide= package's MCP HTTP server handling
a request from the =claude= CLI.

*Root cause*: =claude-code-ide-mcp-http-server.el= (in
=~/.config/emacs/.local/straight/repos/claude-code-ide.el/=, pulled via this
repo's =packages.el= =:host github :repo "manzaltu/claude-code-ide.el"=
recipe) signals a custom =json-rpc-error= condition at three call sites —
=--dispatch= on an unrecognized top-level method (line ~193), =--handle-tools-call=
on an unknown tool name (~228), =--validate-args= on a missing required
argument (~301) — but the symbol was never registered via =define-error=.
An unregistered condition has no =error-conditions= property, so Emacs's
own =(get 'json-rpc-error 'error-conditions)= returns nil; the =condition-case=
around the request handler (=--handle-post=) only catches
=json-parse-error=, =quit=, and =error=, none of which match an
unregistered symbol. The signal escapes the =condition-case= entirely and
propagates out of the process filter, where Emacs's default error printer
falls back to "peculiar error: SYMBOL, DATA..." for exactly this
case — a signal whose car isn't a recognized error type. Net effect: instead
of the client getting a proper JSON-RPC error response for an unsupported
method (e.g. a =resources/list= or similar call the CLI's MCP client sends
that this server's =--dispatch= doesn't implement), the whole request
handler crashes.

*Fix* (patched directly in the straight repo checkout, not this repo — see
"Durability" below):
#+begin_src emacs-lisp
;; After (defvar claude-code-ide-mcp-server--current-session-id):
(define-error 'json-rpc-error "JSON-RPC error")

;; In claude-code-ide-mcp-http-server--handle-post's condition-case, added
;; before the existing (error ...) clause:
(json-rpc-error
 (claude-code-ide-debug "JSON-RPC error: %s" (error-message-string err))
 (claude-code-ide-mcp-http-server--send-json-error
  request nil (nth 1 err) (nth 2 err)))
#+end_src
=define-error='s default parent is =error=, so this alone would already stop
the crash (the existing generic =error= clause would catch it); the
dedicated clause additionally preserves the original JSON-RPC error code and
message instead of re-wrapping everything as a generic =-32603 "Internal
error: ..."=. Verified via =doom sync= (recompiled the stale =.elc= — the
build dir's =.el= is a symlink to the repo, but Emacs's default
=load-prefer-newer=-nil behaviour would otherwise keep loading the old
compiled version) followed by a clean =doom doctor=.

*Durability*: this is a patch to vendored upstream source
(=manzaltu/claude-code-ide.el=), not to anything in this repo, so it isn't
captured by this repo's own git history. It lives in straight's local repo
checkout and will survive an ordinary =doom sync=, but a future =doom
upgrade= (or any operation that re-pulls/resets that straight repo from
upstream) will silently drop it and reintroduce the crash.

*Revisit condition*: if =doom upgrade= (or =SPC h p u=/=doom sync -u=)
touches the =claude-code-ide= package, re-check whether
=claude-code-ide-mcp-http-server.el= still lacks a =json-rpc-error=
=define-error= and a matching =condition-case= clause in =--handle-post=
before assuming this is fixed; re-apply this patch if so, or drop this entry
if upstream has since fixed it properly (worth filing as an upstream issue/PR
against =manzaltu/claude-code-ide.el= rather than re-patching locally
forever — not done yet, no explicit go-ahead given for opening one).

*Symptom*: immediately after =sudo apt install transmission-daemon= on Ubuntu
(transmission =4.0.5=), the service is dead and =systemctl status
transmission-daemon= reports:

Active: failed (Result: timeout) since Sun 2026-08-23 20:07:25 MDT

#+end_example

Note the contradiction that identifies the class of bug: =status=0/SUCCESS=

*Cause*: the shipped unit is =Type=notify=, so systemd waits for an
=sd_notify(READY=1)= that this build never sends, then times out after 90s and
terminates a perfectly healthy process. Nothing is wrong with the
configuration, the port, or permissions — checking those first is wasted time.

*Confirmation it is not the daemon*: running the identical command in the
foreground as the user works on the first try — =transmission-remote -l=
returns the (empty) torrent table straight away.

*Fix used here* ([[id:adr-torrent-transmission][ADR-030]]): don't repair the system unit — run the daemon as a
*user* unit instead, =~/.config/systemd/user/transmission-daemon.service= with
=Type=simple=, then =systemctl --user enable --now transmission-daemon=. This
solves a second problem at the same time: the packaged unit runs as
=debian-transmission=, which would leave every completed download owned by a
system account instead of the user.

*Two loose ends this left, both closed 2026-08-23*:

- The system unit stayed installed and =enabled=, so it kept failing at every
  boot and showed up in =systemctl --failed=. Harmless (it never binds the
  port, so it cannot conflict with the user unit) but noisy. Closed with
  =sudo systemctl mask transmission-daemon= — run by the user, since the
  agent's shell has no TTY for sudo's password prompt (the same constraint
  that put every =apt install= in this repo in the user's own terminal).
  *Gotcha*: masking prevents future starts but does not clear the failure
  already on record — the unit stays listed in =systemctl --failed= until
  =sudo systemctl reset-failed transmission-daemon= or the next reboot.
- A user unit only lives as long as the login session, so seeding stopped at
  logout. Closed with =loginctl enable-linger james= (=Linger=yes=). Worth
  knowing: this needed *no* =sudo= — polkit allows enabling linger for one's
  own account, so it is one of the few system-state changes the agent can
  make directly.

*Takeaway*: =Result: timeout= together with =status=0/SUCCESS= means a
readiness-protocol mismatch (=Type=notify= vs. a daemon that doesn't notify),
not a broken daemon. Check the unit's =Type== before debugging the service
itself.

* RESOLVED: emacs-everywhere buffers opened with an =#+title:= line from Doom's org file template
:PROPERTIES:
:ID:       tshoot-everywhere-file-template
:END:
:LOGBOOK:
- Resolved [2026-08-23 Sat]
:END:

*Symptom*: pressing =Ctrl+Alt+Space= ([[id:adr-everywhere-direnv][ADR-032]])
opened the emacs-everywhere frame, but the buffer was not empty — it started
with a line like:

: #+title: Emacs Everywhere 20260823 141530 Firefox

Everything else worked. Left unnoticed, that line is *pasted back into the
source application* along with whatever you typed, since emacs-everywhere
copies the whole buffer on =C-c C-c=.

*Root cause*: an interaction between three separately-correct behaviours.

1. =emacs-everywhere= opens a brand-new temp file,
   =/tmp/emacs-everywhere-<timestamp>-<app-class>=, with *no extension*. It
   therefore visits in =fundamental-mode=, and at that moment no
   =+file-templates-alist= rule matches.
2. =emacs-everywhere-apply-major-mode= (an =emacs-everywhere-init-hooks=
   member) then switches the buffer to =org-mode=. It picks org rather than
   markdown because =emacs-everywhere-major-mode-function= defaults to
   =#'org-mode= whenever =pandoc= is on =PATH=, and =/usr/bin/pandoc= is
   installed here.
3. Doom's =:editor file-templates= checks on =doom-switch-buffer-hook=, *not*
   =find-file-hook= (=editor/file-templates/config.el:180=). So the check runs
   again on the next switch into that buffer — by which point every condition
   in =+file-templates-check-h= passes: not read-only, empty (=bobp= and
   =eobp=), not a =*special*= buffer, not an org-capture buffer, the file
   still doesn't exist on disk, not modified, not an indirect clone. The
   =(org-mode)= rule matches and expands
   =modules/editor/file-templates/templates/org-mode/__=, whose whole body is
   a =#+title:= derived from =file-name-base=.

Reproduced directly in the running daemon, without needing the hotkey:
visiting the nonexistent path, calling =(org-mode)=, then
=(+file-templates-check-h)= returned a buffer containing exactly
=#+title: Emacs Everywhere 20260823 141530 Firefox=.

*Fix* (=config.el=, [[id:adr-everywhere-direnv][ADR-032]]): inhibit templates
buffer-locally from within emacs-everywhere's own init hooks.

#+begin_src emacs-lisp
(after! emacs-everywhere
  (setq-hook! 'emacs-everywhere-init-hooks +file-templates-inhibit t))
#+end_src

=emacs-everywhere-init-hooks= runs before =emacs-everywhere-mode= and before
any later buffer switch, so this wins the race. =setq-hook!= *prepends*, so the
setter is the first hook member and lands even though a later member can
signal (the package wraps the hook run in =with-demoted-errors=). This is the
same mechanism and the same hook Doom's own =app/everywhere/config.el= uses one
line over to set =doom-inhibit-local-var-hooks=.

Verified after the fix: the same reproduction now leaves the buffer empty, with
=+file-templates-inhibit= =t= and buffer-local.

*Generalisation worth remembering*: any package that opens an extensionless
temp file and *then* sets a major mode can trip Doom's file templates, because
the template check is on buffer-switch rather than file-visit. =org-capture= is
special-cased in =+file-templates-check-h= by name; nothing else is.

* OPEN (workaround known): =emacsclient= output is swallowed by the rtk Bash hook
:PROPERTIES:
:ID:       tshoot-rtk-swallows-emacsclient
:END:

An agent running =emacsclient -e '...'= through its Bash tool gets *completely
empty output* — no value, no error, no diagnostic. The failure is silent and
looks exactly like a dead Emacs server, which sends you off diagnosing the
wrong thing entirely.

Reproduction, run with the Emacs server *deliberately down* (so every call
below should have printed a socket error):

#+begin_example
$ emacsclient -e '"hello"'      # → nothing
$ emacsclient -e '(+ 1 1)'      # → nothing
$ emacsclient -e '(list 1 2)'   # → nothing
$ rtk proxy "emacsclient -e '(+ 1 1)'"
/snap/emacs/.../emacsclient: can't find socket; have you started the server?
#+end_example

Surrounding =echo= statements in the same Bash invocation print normally, so
the whole command block is not being suppressed — only the =emacsclient=
output is. Redirecting to a file and =cat=-ing it back in the same command
also yields nothing, so the output is lost *before* it reaches the shell,
not filtered out of the transcript afterward.

*Cause*: the =rtk hook claude= =PreToolUse= hook in =~/.claude/settings.json=
rewrites Bash commands ([[id:adr-token-reduction-stack][ADR-023]]). =rtk proxy <cmd>= is documented to
execute a command *without* filtering, and it restores the output in every
case tested.

*Workaround*: wrap the whole invocation in =rtk proxy=, which takes one
single-quoted argument — so the elisp needs escaped double quotes inside:

#+begin_example
rtk proxy 'emacsclient -e "(format \"%S\" (list ...))"'
#+end_example

Wrapping the payload in =(format "%S" ...)= is worth doing anyway: it returns
one readable line instead of a bare sexp spread over the reply.

*How to tell this apart from an actually-dead server*: a genuinely dead server
prints =can't find socket; have you started the server?= *through* =rtk
proxy=. If =rtk proxy= also returns empty, the problem is somewhere else.

*Not fully characterised.* This is filed OPEN rather than RESOLVED because the
suppression is not perfectly consistent: earlier in the same session, one
=emacsclient -e '(mapconcat ...)'= call returned its output correctly, while
every later call — including simpler ones — returned nothing. No rule
distinguishing the working call from the failing ones has been established.
Treat =rtk proxy= as the default for =emacsclient= rather than reaching for it
only after a silent failure.

*Related but not the same cause*: [[id:tshoot-agent-shell-system-state][tshoot-agent-shell-system-state]] records the
same symptom class — the agent's own shell reporting wrong results about the
real machine — but predates rtk's installation (ADR-020, 2026-08-13, against
[[id:adr-token-reduction-stack][ADR-023]], 2026-08-23), so rtk cannot explain those earlier failures. What
this entry adds is a second, now-confirmed mechanism for the same kind of
wrongness.

Any =doom= subcommand run from an agent's Bash tool — or from any plain
=subprocess= / pipeline where stdout is not a terminal — can exit non-zero
having printed *nothing at all*. Observed with =doom upgrade= during the
v2.2.2 → v2.2.3 upgrade on 2026-08-24:

#+begin_example
$ ~/.config/emacs/bin/doom upgrade
$ echo $?
1
#+end_example

No error text, no partial progress, no log file. The same command run by hand
in a terminal succeeds normally, which makes this very easy to misread as "the
upgrade is broken" rather than "the invocation is broken".

*Cause*: Doom's CLI writes through its own terminal-aware output layer and
expects an interactive TTY. Without one it aborts early, before it has emitted
anything a caller can see.

*Workaround*: allocate a pseudo-terminal with =script=, which also gives you a
transcript to grep afterwards:

#+begin_example
script -qec "~/.config/emacs/bin/doom sync" /tmp/doom-sync.log
#+end_example

Note that =script= writes =\r\n= line endings, so pipe the log through
=tr -d '\r'= before matching on it.

*Related flags worth knowing while you are here*: =doom= has no =-y=. The
global "assume yes" flag is =--force= (short =-!=), and it goes *before* the
subcommand: =doom --force sync --rebuild=.

*Related*: [[id:tshoot-rtk-swallows-emacsclient][tshoot-rtk-swallows-emacsclient]] is the same class of failure —
a wrapper layer silently eating a subprocess's output — but a different cause
(the rtk Bash hook, not a missing TTY). If a =doom= command is silent, try the
=script= wrapper first; if an =emacsclient= command is silent, try =rtk proxy=.
